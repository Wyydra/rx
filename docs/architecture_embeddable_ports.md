# Rx: The Embeddable Core Architecture

To achieve the ultimate goal of running the **Rx VM both natively at maximum speed and securely inside a Web Browser (via WebAssembly)**, the architecture must evolve to be completely agnostic of the Operating System.

We cannot rely on OS-specific features like `std.DynLib` (.so plugins), Posix threads (`std.Thread`), or direct file system access (`std.fs`) directly within the core VM code.

The solution is the **Embeddable Core (Inversion of Control)** pattern, widely used by engines like Lua, QuickJS, and WebAssembly runtimes.

---

## 1. The Agnostic Core (`rx/src/vm`)

The heart of Rx must become a pure logic engine.
It only knows how to:
- Execute bytecode instructions.
- Allocate and Garbage Collect memory (`Value`, `HeapObject`).
- Pass messages between standard `Actor` instances.

**Rule of thumb:** The `rx/src/vm` directory must never import `std.fs`, `std.Thread`, `std.Io`, or `std.os`. It should compile easily with `zig build -Dtarget=wasm32-freestanding`.

## 2. The `Host` Interface (VTable)

Since the VM cannot do I/O by itself, how do Ports work? 
We define a `Host` interface (a struct of function pointers or a Zig `comptime` interface) that the environment must provide when instantiating the VM.

```zig
pub const Host = struct {
    /// Called when Rx wants to spawn an external port
    spawnPortFn: *const fn (ctx: *anyopaque, name: []const u8) anyerror!ActorId,
    /// Called when an Rx actor sends a message to an external port
    sendToPortFn: *const fn (ctx: *anyopaque, port_id: ActorId, msg: Value) void,
    // ...other necessary hooks...
};
```

When you initialize the Scheduler, you pass the `Host` to it:
```zig
var scheduler = Scheduler.init(allocator, 0, &system, my_host);
```

## 3. The Two Environments

### Environment A: Native CLI (`rxt`)
When building the standalone `-OReleaseFast` native executable (`rxt`):
- `rxt/src/main.zig` implements the `Host` interface using **Zig's native OS features**.
- `spawnPortFn` will use `std.Io.concurrent` to spawn a real OS thread and an asynchronous `std.Io.Queue`.
- The native environment can register an infinite number of highly optimized Ports (Network, Filesystem, SDL) written in Zig or C, linked at **compile-time**.

### Environment B: WebAssembly (`wasm`)
When compiling the VM for the browser (`zig build -Dtarget=wasm32-freestanding`):
- The `Host` interface is implemented using **JavaScript Interop**.
- `spawnPortFn` simply registers a JavaScript callback using `extern "env" fn rx_spawn_js_port(...)`.
- When Rx sends a message to a Port, the Wasm module triggers the JavaScript function, allowing Rx to interact with the DOM, WebSockets, or Canvas, entirely asynchronously.

---

## 4. The Compile-Time Port Registry

Instead of `std.DynLib` (which forces you to compile `.so` files separately), we will use Zig's powerful build system to inject Ports at compile-time for the native executable.

In `rxt/build.zig`, you pass a list of Zig files (the ports). The build system generates a `ports_registry.zig` file:

```zig
// Auto-generated by build.zig
pub const available_ports = .{
    .console = @import("ports/console.zig").init,
    .http = @import("ports/http.zig").init,
};
```

When the `rxt` executable starts, it automatically registers all these native ports into the `Host`, offering native C-like performance (because everything is inlined by LLVM) while retaining a plugin-like developer experience.

## Summary: Why this is the ultimate architecture

1. **Extreme Performance**: Compile-time linking means LLVM optimizes the VM and the Ports together. No `dlopen` overhead, no FFI walls.
2. **True Cross-Platform**: The `rx` module becomes a pure dependency. You can drop it into any Zig, C, C++, or Rust project, or compile it to Wasm for the Browser.
3. **No Compromises**: The Native `rxt` CLI still gets the ultra-fast lock-free ThreadPool (`std.Io`) queue for its ports, while the Browser version gets seamless JS-event-loop integration.
